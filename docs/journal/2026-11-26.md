## 4. Kernel and bootloader

Linux 7.1.8 was configured using a version-controlled fragment approach rather than relying on interactive menuconfig. The intended architecture is a common baseline plus hardware-specific configuration fragments. Built-in ext4, GPT and VirtIO storage support allow the QEMU root filesystem to mount without an external initramfs.

The installed kernel release is `7.1.8-ainow-genesis`. The boot directory contained a 15 MiB kernel image, 9 MiB System.map and 147 KiB configuration. The boot log identifies GCC 16.2.0 and GNU Binutils 2.47.20260726 as the kernel build tools.

The first bootloader preflight returned an empty `lsblk PARTTYPE` field. Direct probing with `blkid -p` confirmed GPT and the BIOS Boot Partition type GUID `21686148-6449-6e6f-744e-656564454649`. This is a metadata discovery issue, not evidence of a missing partition. The guarded installation targeted the whole loop device backing the project image, never a physical disk. GRUB 2.14 reported successful i386-pc installation. The earlier attempt to write grub.cfg before the directory existed failed; the successful sequence installed GRUB first, then wrote and checked the configuration.

GRUB searches by filesystem UUID; the kernel receives root=PARTUUID because no external initramfs is used. Normal and serial-debug entries were configured. The chroot exited, virtual mounts were released, and the image was unmounted and detached before QEMU opened it.

## 7. Distribution engineering decisions

AI-Now Linux is a company engineering platform. Support only the hardware actually used by the company. Separate hardware targets (CPU, drivers, firmware, kernel configuration) from software profiles (engineering, AI, embedded and desktop).

The package manager must support compiling from source and installing prebuilt binaries. A source build should stage and package files before installation, so both paths share one installation engine and database. Git repositories hold recipes, source references and patches; release assets can distribute binaries without bloating Git history. Upload, download and install are distinct operations. Authentication, signed metadata, dependency handling, safe archive extraction, configuration preservation and ABI compatibility must be designed explicitly.

Proposed implementation: Python CLI and curses menu, Bash recipes, TOML metadata, SQLite database and tar.zst archives with a provisional `.ainpkg` extension. These are design proposals, not implemented capabilities. OpenSSH is the first package acceptance target; host keys must be generated per installation and private keys must never be bundled.

## 10. Chapter 11 — Hybrid source/binary package manager

This entry follows the Genesis checkpoint retrospective above. The repository had the package design in the README and Day 03 journal; no committed prototype was present at baseline `c0e99f7`. Implementation follows the existing Python/Bash/TOML/SQLite and tar.zst design.

- The native source builder exports a reviewed Git recipe to a temporary workspace, validates the upstream SHA256, builds without elevated privileges and packages its isolated `DESTDIR`. Both source output and downloaded binaries enter the same install path. The manifest records the recipe commit and the architecture, glibc and CPU baseline labels.
- `ainpkg` preflights archive, filesystem and ownership conflicts. SQLite records packages, file digests and modes. A target lock serializes operations. An undo table records file contents and modes across interruptions. Locally modified configuration survives upgrades and removal. Direct-to-root `make install` was avoided because it would bypass package ownership and recovery.
- GitHub releases supply binary transport through `gh`, with separate upload and download commands and a trusted SHA256 check before accepting a download. The CLI upload preserves existing release assets. The first test run exposed incorrect positional argument handling in the fake `gh` program. The stub was corrected and the full suite passed.
- The first recipe pins OpenSSH Portable 10.6p2 to the SHA256 in the [upstream release notes](https://www.openssh.org/releasenotes.html). The x86-64 recipe uses the upstream install-without-keys target, clears the setuid bit on `ssh-keysign` and includes the upstream license.

| Verification | Actual result |
|---|---|
| Python 3.12.14 automated tests | 13 passed, including malformed payloads, link rejection, ownership collisions, competing installs, configuration preservation, rollback and interrupted-transaction recovery |
| Bash syntax and Git whitespace checks | Passed |
| Source input and Git recipe | Built from the pinned Git recipe and SHA256-verified source. Cached local input and HTTPS retrieval both succeeded |
| Reproducibility | Two OpenSSH builds on the same x86-64/glibc 2.41 host from the same recipe revision produced byte-identical packages. Recipe Git subtree `38b4c32a862f590392b81525b5af952e81bc4d8d`. Local package SHA256 `8592011a85943c3fe2ca32a7237cb99bdabca83ca070e53b90d6dd48868fa484` |
| OpenSSH package lifecycle | Installed and verified in a disposable root. `ssh -V` and `sshd -V` reported OpenSSH 10.6p2 with OpenSSL 3.5.9. No host keys were staged. Reinstallation and removal preserved the edited `sshd_config` |
| Compatibility gate | The host-built glibc 2.41 package was rejected by a disposable root labeled glibc 2.44 |
| Binary release workflow | Automated tests used a stub `gh` and exercised success, checksum failure and existing-output protection. Live GitHub asset transfer remains unverified |

Testing used temporary directories. No physical disks or Genesis RAW image were modified. The source package and build logs remained outside Git. The Chapter 11 branch is based on `c0e99f7`. Its commit records the implementation, test suite and this journal together for review.

### Package inspection and transaction preview

Follow-up on the Chapter 11 branch added `ainpkg inspect`, read-only previews for installation and removal, and unchanged-file reuse on reinstallation. Preview uses the same ownership, compatibility and configuration preflight as the write path. It refuses pending recovery so a preview cannot replay earlier changes.

The suite passed 17 tests on Python 3.12.14. Four new checks cover manifest inspection without a target, accurate upgrade and removal previews with unchanged SQLite contents, interrupted transactions left untouched during preview, and preservation of the inode on identical reinstalls. Testing used temporary roots.
