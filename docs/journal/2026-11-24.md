## 1. Purpose and engineering philosophy

The project began as a return to Linux From Scratch after decades of computer engineering experience. Its purpose is not merely to install Linux, but to understand and control the construction of an operating system, establish a reusable distribution foundation, and eventually investigate kernel engineering. The initial deliverable is a bootable x86-64 command-line system, not a production-ready distribution.

The project will ultimately integrate original C, C++ and Python utilities. The first build is manual to establish a reference procedure; the second should automate that procedure; subsequent builds should support modular product configurations. This is a proposed strategy, not an implemented build engine.

### 3.2 Virtual disk and incident report

```sh
qemu-img create -f raw images/ai-now-linux.raw 80G
sudo losetup --find --show --partscan images/ai-now-linux.raw
```

The raw image has a logical size of 80 GiB (85,899,345,920 bytes), initially occupying only 4 KiB on the host. Sparse allocation saves host storage until blocks are written. Raw format was chosen for straightforward loop-device access; qcow2 is an alternative for VM snapshots, but is less direct for this workflow.

The assistant accidentally repeated the disk creation instructions, resulting in two loop mappings, `/dev/loop19` and `/dev/loop26`, to the same backing inode 38703350. The user identified the duplication. Both mappings were unpartitioned and unmounted when checked. The duplicate was detached with `sudo losetup -d /dev/loop26`; verification showed only `/dev/loop19` remained and the image still occupied 4 KiB. Recreating an existing raw image can destroy data. Future automation must check file existence, use `losetup --nooverlap` where appropriate, verify the backing file, and never assume loop numbers remain constant.

Physical disks `/dev/nvme0n1` and `/dev/sda` were not partitioned or formatted.

### 3.3 Partitioning and filesystem

Used `fdisk /dev/loop19` to create GPT, then a 2 MiB BIOS boot partition and a Linux filesystem partition occupying the remaining usable space. Wrote the partition table only after inspecting it.

| Partition | Sectors (512 bytes) | Purpose |
|---|---|---|
| loop19p1 | 2048–6143 | BIOS boot, 2 MiB, no filesystem |
| loop19p2 | 6144–167770111 | Linux root filesystem |

GPT identifier: `C813F538-0FA2-4037-9632-479917CC602E`.

The BIOS boot partition reserves space for GRUB's embedded core image when booting GPT with legacy BIOS. It is not an EFI System Partition. UEFI would require a different boot layout. GRUB has not yet been installed.

```sh
sudo mkfs.ext4 -L AINOW-ROOT /dev/loop19p2
sudo mkdir -p /mnt/lfs
# Verified mountpoint was not mounted and directory was empty.
sudo mount /dev/loop19p2 /mnt/lfs
export LFS=/mnt/lfs
```

Verified ext4 UUID `cf7b7e99-cf6b-470d-9fe1-87b9742e72af`, read/write mount, 20,970,496 4 KiB blocks, 5,242,880 inodes and a 131,072-block (512 MiB) journal. `df` reported 79G total and 75G available; the image occupied 519M on the host after formatting. The journal supports filesystem crash recovery; `lost+found` supports recovery of disconnected filesystem objects. Default filesystem settings and reserved blocks were retained. No custom tuning or swap partition was introduced.

## 4. Chapter 3 — Packages and patches

The initial `grep -i '<title>'` command returned only the opening HTML tag because the title spanned lines. A subsequent context search found the section title, and searching for `Linux From Scratch|Version` confirmed the actual book version: 13.1-systemd.

```sh
export LFS=/mnt/lfs
mountpoint -q "$LFS" && sudo mkdir -pv "$LFS/sources" && sudo chmod -v a+wt "$LFS/sources"
```

The mount guard prevents accidentally creating build directories on the host root filesystem. Mode 1777 permits shared writing while the sticky bit restricts deletion/renaming of other users' entries. Verified `drwxrwxrwt root root`.

Pinned the exact upstream source list and checksums in a project-specific `manifests/` directory:

```sh
mkdir -p manifests
export LFS_VERSION=13.1-systemd
export LFS_BOOK="https://www.linuxfromscratch.org/lfs/view/$LFS_VERSION"
printf '%s\n' "$LFS_VERSION" > manifests/lfs-version.txt
wget -O manifests/wget-list-systemd "$LFS_BOOK/wget-list-systemd" &&
wget -O manifests/md5sums "$LFS_BOOK/md5sums"
mountpoint -q "$LFS" && wget --input-file=manifests/wget-list-systemd --continue --directory-prefix="$LFS/sources"
cp manifests/md5sums "$LFS/sources/"
( cd "$LFS/sources" || exit 1; md5sum -c md5sums )
mountpoint -q "$LFS" && sudo chown root:root "$LFS"/sources/*
```

Both manifests returned HTTP 200; 94 lines each, 6,085 and 5,160 bytes respectively. Downloaded 94 files (86 archives and 8 patches), 628M, in 7m 11s wall time (5m 48s transfer time). All 94 checksum results were OK. Source directory contained 95 files including the checksum manifest. Root ownership was applied without a reported error. MD5 detects accidental corruption but is not a modern authenticity guarantee; future distribution infrastructure should use strong hashes and signed metadata. The manifest directory is our project convention, not an LFS requirement.

### 4.1 Why the packages exist

A Linux distribution is assembled from cooperating layers: kernel, userspace ABI and libraries, toolchain, system services, shell utilities, and applications. Not every downloaded component is required at runtime; some exist to build, test or document the system. The kernel provides system calls, scheduling, memory management and device access; Glibc supplies the userspace C library and dynamic loader. GCC, Binutils and their mathematical dependencies establish the compiler toolchain. Systemd initializes and supervises services; GRUB loads the kernel. Bash and utilities provide an interactive operating environment. Build ordering matters because the compiler and libraries must be bootstrapped without accidental dependence on the host.

The appendix inventories every verified download with its purpose. Detailed dependency edges, configuration flags, installation and verification will be documented when each component is actually built. Do not confuse downloaded packages with installed packages.

## 5. Architectural insight — From DOS to Linux

The project owner recognized the overall construction sequence from earlier personal computer experience: `FDISK`, `FORMAT C:`, `SYS C:`, then install the necessary operating environment. The analogy is conceptual: DOS SYS transfers existing boot/system files, whereas LFS compiles a toolchain and userspace, builds a kernel and installs a bootloader. At today's checkpoint we have only prepared the disk and downloaded sources, not performed the equivalent of a successful SYS C:.

Likewise, Windows 3.1 running above DOS recalls a graphical environment above a Linux base system. `WIN` and `startx` are useful historical parallels, not architectural equivalences. Windows 3.1 includes more than window management; X11 separates display server and window manager, while a Wayland compositor combines display and composition responsibilities. The GUI is a choice of interface rather than the entirety of the operating system. Possible interfaces include pure CLI, KMSCON/TUI, Openbox/X11, Sway/Wayland, and an AI-native voice/vision/agent interface. A custom C/C++ window manager is another research possibility.

Prior DOS and embedded/Yocto experience makes basic disk and package operations familiar. Future teaching should accelerate routine work while retaining engineering documentation, and focus on toolchain bootstrap, kernel configuration, boot, system services, dependency management and automation. LFS is useful even if the underlying architecture is already understood.

## 6. Distribution design — One Core, Multiple Profiles

The owner explicitly requested these future command interfaces:

```sh

./build.sh --profile enterprise
./build.sh --profile embedded
./build.sh --profile ai-appliance
```

Personal targets workstations/development; enterprise targets servers and infrastructure; embedded targets dedicated devices and industrial systems; ai-appliance targets AI compute and agent interfaces. All share a common foundation where practical; profiles select packages, kernel configuration, hardware support, services, security policies and applications. Cross-architecture support is a future goal, not demonstrated.

Proposed repository structure (not all directories exist yet):

```text
ai-now-linux/
  build.sh
  core/
  manifests/
  profiles/{personal,enterprise,embedded,ai-appliance}/
  packages/
  configs/
  scripts/

```

LFS provides a transparent baseline; Yocto provides mature recipe/layer-based embedded image construction. Our project can learn from both without claiming to replace Yocto. Potential commercial direction: end-to-end system solutions, including custom hardware, operating systems and AI software for devices such as AION and Neris systems. Maintainability, reproducibility, security updates, package management, licensing compliance and rollback must be designed before commercial deployment.

## 7. USB Network Build Installer — proposed

The owner proposed booting from USB and constructing a desired Linux system from the network. A minimal bootable environment would detect CPU, GPU, storage and networking, retrieve signed manifests from an AI-Now repository, accept a profile or custom configuration, then download, build, configure and install the selected system. A terminal interface is sufficient.

Three proposed modes: binary installation for speed, source build for maximum customization, hybrid build for prebuilt base components plus selected source rebuilds. This resembles aspects of Debian netinstall, Gentoo and Yocto. A source build needs sufficient temporary disk, memory, CPU time and reliable networking; embedded targets may require cross-compilation on a separate host. A hybrid system needs compatible ABIs and dependency resolution. A USB installer must explicitly confirm the destination disk before destructive operations, support BIOS/UEFI as applicable, validate signatures, and handle interruptions and recovery.

Configuration-as-code could allow `./build.sh --config neris-a.yaml`, with declarative architecture, kernel, packages, interface and AI runtime selections. This is a design concept, not a supported command yet.

Tentative assistant-proposed milestones: 0.1 Genesis bootable CLI; 0.2 automated build engine; 0.3 profiles; 0.4 binary repository; 0.5 USB network installer; 0.6 hardware-aware configuration; 1.0 mature customizable distribution. These are not release commitments.

## 8. Kernel engineering research direction

The owner identified kernel development as a deeper interest. Distribution engineering assembles a system; kernel engineering implements or modifies its privileged core. Finish the LFS baseline as an experimental platform. Separately investigate whether to modify Linux or write an original educational kernel; no choice has been finalized.

Proposed original-kernel study sequence: bootable hello world; serial console; GDT/IDT and exceptions; hardware interrupts; physical memory allocator; paging; scheduling; user mode and syscalls; VFS; shell and user programs; SMP; networking. Suggested tools are C, x86-64 assembly, GNU toolchain, QEMU, GDB and Vim. None of these original-kernel milestones has been implemented.
